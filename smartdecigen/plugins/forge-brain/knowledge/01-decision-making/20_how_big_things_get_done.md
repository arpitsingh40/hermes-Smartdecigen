# V20 · HOW BIG THINGS GET DONE — Bent Flyvbjerg & Dan Gardner
Tier 5 · Systems / Execution · Tree Memory

## ROOT — the deepest truth
Projects fail by a universal pattern — committing fast on optimism, then discovering reality slowly and expensively — and succeed by the inverse: THINK SLOW (cheap, thorough, experiment-rich planning), ACT FAST (short delivery windows that give black swans no time to strike), and forecast from the REFERENCE CLASS, never from your own excitement.

## TRUNK — core thesis
From the largest project database on earth (16,000+ projects): only 8.5% hit both budget and schedule; 0.5% hit budget, schedule, AND benefits. The Iron Law: over budget, over time, under benefits, over and over. Causes: uniqueness bias ("our case is different"), the planning fallacy at scale, strategic misrepresentation (lowballing to win approval), and lock-in before learning. Cures: reference-class forecasting (anchor on the distribution of similar past projects), Pixar-style iterative planning (cheap simulations before expensive commitments), MODULARITY (build from repeatable Lego blocks that learn with each repetition), experienced masterbuilders over enthusiastic first-timers, and right-to-left thinking — start from the box you must deliver, not from what you feel like starting with.

## BRANCHES & LEAVES

### Branch 1 — Think slow, act fast
├─ Planning is cheap; delivery is where money and reputations burn — so maximize learning in the cheap phase
├─ The delivery WINDOW is black-swan exposure: the longer a project stays open, the more chances for a lethal surprise (a pandemic, a funding winter, a platform policy change)
└─ LEAF: compress the founder's launch/delivery windows ruthlessly; a 6-week pilot beats a 6-month build for reasons beyond speed — it's exposure math

### Branch 2 — Reference-class forecasting (outside view, industrialized)
├─ Find the class ("D2C brands entering modern trade"), get its distribution (costs, time, failure rates), anchor THERE, adjust minimally
├─ Uniqueness bias is the enemy: "our case is different" is the most expensive sentence in project history
├─ Fat-tailed project types (IT projects famously) need extra margin: the mean is not the risk — the tail is
└─ LEAF: every founder estimate gets the question "what did this cost/take for the last ten who did it?" — and if the class is fat-tailed, plan for the tail, not the average

### Branch 3 — Experiment and experience (the Pixar model)
├─ Pixar makes the cheap version many times (scripts, storyboards, animatics) before the expensive version once
├─ EXPERIENCE embedded in the team and tech is the other pillar: proven components, practiced people — first-timers doing first-of-a-kind is the worst square
└─ LEAF: before any big founder commitment, ask "what's the storyboard version?" and "who on this has done it before?" — rent the experience if you lack it

### Branch 4 — Modularity: the Lego principle
├─ Big things succeed when built from small repeatable modules (solar farms, ships in series, cloud data centers) — each repetition slides down the learning curve
├─ One-huge-thing projects (nuclear plants, Olympics) can't iterate — every one is a first attempt
└─ LEAF: redesign the founder's big move as repeated modules: one store playbook × 80 stores, one city template × N cities — the SECOND unit is where profit hides

### Branch 5 — Right-to-left thinking & the premortem gate
├─ Start from the delivered outcome ("the box on the right") and reason backward to today — prevents means becoming ends
├─ Commitment escalates: approvals based on lowballed numbers create zombie projects nobody can kill
└─ LEAF: define 'done and successful' in measurable terms BEFORE starting; pre-agree the kill criteria while nobody's ego is invested yet

### Branch 6 — Strategic misrepresentation (the politics of estimates)
├─ Numbers presented to win support (from co-founders, investors, spouses) drift from numbers believed — often unconsciously
└─ LEAF: keep two sets honest: the pitch number and the planning number; the engine holds the founder to planning on the REAL one

## FRUIT — how SmartDecigen applies this
- WHEN a founder estimates time/cost for a launch → APPLY reference-class: demand the base-rate distribution of comparable attempts; adjust from there, tail-aware.
- WHEN a big build is proposed → APPLY Pixar test: design the cheapest full-loop simulation (landing page, pilot batch, pre-orders) before committing capital.
- WHEN expansion is on the table → APPLY modularity: convert the plan into a repeatable unit + learning loop; validate unit #1 economics before unit #2.
- WHEN a project drags open-ended → APPLY window compression: shrink scope until the delivery window is weeks, not quarters — time open = swan exposure.
- WHEN commitment hardens early → APPLY right-to-left + kill criteria: define done, define dead, both in numbers, both now.
