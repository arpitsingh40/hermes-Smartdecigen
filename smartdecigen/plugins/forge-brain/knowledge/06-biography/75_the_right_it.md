# V75 · THE RIGHT IT — Alberto Savoia
Tier 6 · Founder Stories · Tree Memory

## ROOT — the deepest truth
Most new products fail not because they were built wrong but because they were the WRONG IT — a solution to a problem that doesn't exist or a problem that customers don't care about enough to change their behavior; the only way to avoid this is to pretotype — test whether the RIGHT it EXISTS before you invest in building it at all.

## TRUNK — core thesis
Savoia's data: 80-90% of new products fail, and post-mortem analysis shows that the #1 cause is not poor execution — it's building something nobody actually wants (or wants enough). The cure is PRETOTYPING — a set of techniques cheaper and faster than prototyping because you test the fundamental assumptions (does anyone want this? will they use it? will they pay?) before building any facade, let alone a product. Key techniques: the FAKE DOOR (run an ad or landing page for a product that doesn't exist — count click-through as demand), the PINOCCHIO (build a manual version of the supposed automation — if no one uses it, automation won't help), the CUSTOMER-DRIVEN (get a purchase order for the product that doesn't exist yet), the MECHANICAL TURK (fake the backend with humans), and the MINI-MARKET (start with one small segment before going broad). The core principle: "make sure you are building The Right It before you build It right" — and the way to know is data from the cheapest possible experiment, not opinion.

## BRANCHES & LEAVES

### Branch 1 — The failure pattern
├─ 80-90% of new products fail; the primary cause is "the wrong it" — not execution, not timing, not competition
├─ Founders fall in love with their solution and skip the step of testing whether the problem is real and urgent
├─ The emotional hurdle: it's easier to build a product (which feels productive) than to test an assumption (which feels like stopping)
└─ LEAF: before any product investment, ask: "what evidence exists that customers actually have this problem AND are motivated to solve it?" — if the answer is "I think so," it's time to pretotype

### Branch 2 — The pretotyping techniques
├─ Fake Door: buy Google Ads for a product that doesn't exist yet — clicks = evidence (with a clear landing page explaining it's not available)
├─ Pinocchio: provide the service manually before building any automation — if no one signs up, software won't help
├─ Mechanical Turk: fake the AI/backend with humans — if the manual version doesn't work, the automated one won't either
├─ Customer-Driven: get a signed purchase order or LOI before building — if they won't commit, they don't need it enough
└─ LEAF: choose the CHEAPEST pretotype that can falsify the core assumption — the goal is to get a NO fast, not to get a YES

### Branch 3 — Imperfection over inaction
├─ A pretotype is intentionally crude, incomplete, and potentially embarrassing — that's the point
├─ The choice is not between a crude pretotype and a polished prototype — it's between a crude pretotype and NOTHING (because most products never get built, and most of those that do fail)
├─ The founder's fear: "what if the test fails and I look stupid?" — reframed: "what if I spend 6 months building the wrong thing?"
└─ LEAF: the rule: if you can't run a pretotype in one week for under $1,000, your assumption is too abstract — make it testable first

### Branch 4 — Data trumps opinion
├─ The founder's opinion, the investor's opinion, and the expert's opinion are all worth LESS than one customer behavior
├─ The pretotype is the discipline of turning opinions into falsifiable hypotheses and then testing them cheaply
├─ "I know my customers" is not data — it's a hypothesis. Pretotyping reveals whether it's true
└─ LEAF: when a founder says "I know this will work because I understand the market," ask: "what's the cheapest test that could prove you wrong in one week?"

### Branch 5 — The Right It mindset
├─ The goal is not to prove your idea is right — it's to discover the Right It as fast as possible
├─ When the pretotype fails (the fake door gets no clicks, the Pinocchio gets no signups), that's SUCCESS — you avoided months of wasted building
├─ The discipline: keep testing different "its" until one produces real demand — then build THAT
└─ LEAF: the founder should aim to kill three ideas a month through pretotyping — each kill is a saved year of misdirected execution

## FRUIT — how SmartDecigen applies this
- WHEN a new product is proposed → APPLY the pretotype-first rule: what is the cheapest test that can falsify the core assumption? Do that before any spec.
- WHEN a founder insists they "know the market" → APPLY the fake door test: one landing page, one week, one ad budget — the clicks don't lie.
- WHEN a feature request emerges → APPLY the Pinocchio test: provide it manually first — if usage doesn't materialize, don't build it.
- WHEN a team debates priorities → APPLY the Right It question: "are we debating how to build something that might be the Wrong It?" — if yes, pretotype first.
- WHEN a project is autopsied → APPLY the 80-90% reframe: failure is likely not execution — it's the Wrong It; what assumption was untested?
