# V135 · ESCAPING THE BUILD TRAP — Melissa Perri
Tier 3 · Product · Tree Memory

## ROOT
Most companies are stuck in the "build trap" — prioritizing output (features shipped) over outcomes (problems solved, value created). Perri diagnoses how organizations fall into this trap: when strategy is absent or unclear, when product managers act as project managers, when roadmaps are feature lists rather than problem statements, and when success is measured in story points. Escaping requires: good product strategy, empowered product teams, outcome-based roadmaps, and a product management discipline that connects strategy to daily work.

## TRUNK
The product management hierarchy: (1) Vision — why the company exists, 5-10 year horizon. (2) Strategy — the logical path from current state to vision, answering "what problems will we solve, for whom, in what sequence?" (3) Objectives — specific, measurable outcomes that indicate strategic progress. (4) Roadmap — the problems to solve this quarter, organized by objective, NOT feature lists. (5) Discovery and delivery — the continuous process of finding and shipping solutions. The build trap happens when the strategy layer is missing — teams get features from stakeholders without understanding WHY, and nobody connects features to outcomes.

## BRANCHES
- Product strategy: the "strategic framework" = vision + strategic intents + product initiatives. Vision is aspirational. Strategic intents are the current challenges (e.g., "win the mid-market segment"). Product initiatives answer "how will we accomplish each intent?"
- Outcome-based roadmaps: each item = problem to solve + desired outcome metric. Never: "build a dashboard." Always: "improve new user activation rate from 15% to 25%."
- Product manager role: not a project manager, not a mini-CEO. The PM is responsible for VALUE (does the solution solve a real problem?) and VIABILITY (does it work for the business?). The PM discovers what to build; the team builds it.
- Killing features: a feature that solves no real problem is debt, not an asset. Regular "kill audits" — sunset features that aren't contributing to outcomes. Measure feature adoption and usage decay.

## FRUIT
- WHEN the roadmap is a feature list → APPLY outcome reframe: rewrite each roadmap item as "problem statement → desired outcome metric."
- WHEN a feature request comes from leadership → APPLY problem extraction: "what problem are we solving, and how will we measure success?"
- WHEN features aren't being used → APPLY kill audit: what features have <5% adoption after 6 months? Sunset them.
- WHEN the team feels like a feature factory → APPLY strategy check: do they know the vision and strategy, or are they just receiving tickets?

## SEEDS
- "Build trap: measuring success by features shipped, not problems solved."
- "Your roadmap should describe outcomes, not features."
- "If you can't trace a feature to a strategic objective, don't build it."
- "Sunset features with <5% adoption. Dead features are organizational debt."
- "Product managers discover the problem. Teams discover the solution."

## GRAFTS
- → Inspired: the empowered product team model that escapes the build trap.
- → Good Strategy/Bad Strategy: the kernel (diagnosis, guiding policy, coherent actions) = product strategy.
- → The Lean Startup: the Build-Measure-Learn loop that validates outcomes.
